# 05. RAG Pipeline: відповідь на запит про характеристику

Мета шару — на запит користувача дати **максимально точну** відповідь про характеристику товару, з цитатою джерела й датою, а при конфлікті — з чесним показом розбіжностей. Центральна ідея: **fact-first маршрутизація** — спершу пробуємо детермінований lookup у canonical store, і лише потім векторний пошук.

## 1. Загальний потік

```
Запит користувача
   │
   ▼
[1] Query Understanding  ── витягти товар + запитуваний атрибут + намір
   │
   ▼
[2] Router
   ├── (A) Exact Fact Lookup   ── товар і атрибут визначені → SQL/function call
   │        └── факт знайдено? ── ТАК ─▶ детермінована відповідь + citation
   │                              └─ НІ ─▶ до (B)
   └── (B) Hybrid Retrieval     ── нечіткий запит / rich-контент / атрибут не мапиться
            └── dense + BM25 + filters ─▶ rerank ─▶ generation with citations
```

## 2. [1] Query Understanding

LLM (structured output) розбирає запит на складові:

```json
{
  "product_mentions": [{"brand": "Acme", "model": "Model X", "raw": "аку модель Х"}],
  "requested_attributes": ["net_weight"],   // мапиться на канон тим же словником/embedding, що й у 03
  "intent": "lookup | compare | filter | explain",
  "constraints": {"category": "headphones"}
}
```

- **Розв'язання товару:** entity resolution проти `products` (GTIN/MPN/brand+model, fuzzy) → `product_id`. Якщо кандидатів кілька — уточнити або показати варіанти.
- **Розв'язання атрибута:** назва атрибута із запиту мапиться на `attribute_key` тим самим механізмом, що й у нормалізації (консистентність запиту й даних — важлива).
- **Класифікація наміру:** lookup (один факт), compare (кілька товарів/атрибутів), filter ("товари з IP67 і вагою <300 г"), explain (потрібен контекст із прози).

## 3. [2A] Exact Fact Lookup — головний маршрут точності

Коли товар і атрибут однозначно визначені:

- Прямий запит до fact store: `product_id + attribute_key + effective=true + superseded_by IS NULL`.
- Реалізація через **function calling / Text2SQL** над безпечним, обмеженим набором функцій (не сирий SQL від LLM).
- Якщо факт є — відповідь **детермінована**: беремо `canonical_value`/`original_value`, одиницю, провенанс. LLM лише форматує, **не вигадує число**.
- `disputed=true` → показати конкуруючі значення з джерелами, а не одне.
- Для `intent=filter/compare` — параметризований запит по багатьох товарах (WHERE по атрибутах, JOIN по product_id), результат — таблиця.

Це маршрут, який дає максимальну точність для типового питання "яка характеристика X у товару Y".

## 4. [2B] Hybrid Retrieval — fallback

Спрацьовує, коли: атрибут не мапиться на канон, запит про rich-контент ("чи підходить для дощу?"), товар нечіткий, або факт відсутній у store.

1. **Фільтр метаданих:** звузити до `brand`/`category`/`product_id`, `effective=true`.
2. **Dense + BM25** у відфільтрованому підмножині → кандидат-чанки.
3. **Reranking:** cross-encoder переранжовує top-N за релевантністю саме до запиту (набагато точніше за суто векторний скор).
4. Передати top-k чанків у генерацію.

## 5. Генерація відповіді

- **Grounding:** відповідь будується **тільки** з fact-lookup результату або retrieved-чанків; заборонено додавати "знання з голови".
- **Citations обов'язкові:** кожне твердження — з посиланням на `source_url` і `fetched_at`. Для fact-маршруту — з `source_span`.
- **Freshness:** явно вказувати дату факту ("станом на 2026-07-10"), бо характеристики й наявність застарівають.
- **Конфлікти:** при `disputed` — показати обидва значення з джерелами, не "усереднювати" й не приховувати.
- **Чесне "невідомо":** якщо ні lookup, ні retrieval не дали факту — сказати, що даних немає, а не вигадати. Це критично для довіри до системи характеристик.
- **Одиниці:** показувати в зручній користувачу одиниці, але спиратись на канонічну (для порівнянь).

**Приклад відповіді (lookup):**
> **Acme Model X — вага нетто: 2.3 кг.**
> Джерело: сторінка виробника vendor.com, станом на 10.07.2026.

**Приклад (disputed):**
> За даними офіційного фіда — **2.3 кг**; на сторінці товару вказано **2.4 кг**. Джерела розходяться; наведено обидва з посиланнями.

## 6. Порівняльні та фільтр-запити

- **Compare:** lookup потрібних `attribute_key` для кількох `product_id` → таблиця порівняння з канонічними одиницями (коректне порівняння можливе саме завдяки нормалізації з `03`).
- **Filter:** параметричний запит по fact store (напр. `ip_rating='IP67' AND net_weight < 300`) → перелік товарів; за потреби доповнити rich-контекстом.
- Тут перевага fact-first особливо помітна: векторний пошук погано робить числові фільтри й точні порівняння, а SQL по нормалізованих фактах — легко.

## 7. Захист якості відповіді

- **Верифікація grounding:** пост-перевірка, що кожне число у відповіді присутнє в джерелі/факті; інакше — відкинути/перегенерувати.
- **Confidence gating:** факти з дуже низькою впевненістю подавати з застереженням або не подавати.
- **Розв'язання неоднозначного товару:** при кількох кандидатах — уточнююче питання або явний вибір, а не "вгадування".
- **Логування:** запит → маршрут (A/B) → використані факти/чанки → відповідь. Потрібно для еваля й дебагу (див. `06`).

## 8. Чому саме така маршрутизація дає точність

- Точні, добре визначені питання йдуть **повз вектори** — детермінований lookup не має проблеми "знайшлась вага іншого товару".
- Вектори лишаються там, де вони справді сильні: нечіткі, семантичні, rich-контентні запити.
- Нормалізація й провенанс дають коректні порівняння, чесні конфлікти й перевірні цитати.

## 9. Результат шару
