# 06. Quality & Operations: якість, моніторинг, експлуатація

Мета шару — гарантувати, що система залишається **точною в часі**: сайти змінюють розмітку, з'являються нові рушії й таксономії, характеристики застарівають. Без контролю якості й моніторингу точність RAG деградує непомітно.

## 1. Метрики якості (по шарах)

**Crawling:**
- Coverage: частка цільових товарів, успішно зібраних.
- Fetch success rate, частка headless vs static, частка блокувань (403/429/CAPTCHA).
- Свіжість: розподіл віку останнього успішного fetch-у.

**Extraction:**
- Attribute coverage: середня кількість витягнутих атрибутів на товар.
- Розподіл по tier-ах (скільки закрито дешевими Tier 1–3 vs дорогим Tier 4).
- Grounding rate: частка LLM-фактів, що пройшли span-верифікацію.

**Normalization:**
- Auto-map rate: частка атрибутів, змаплених автоматично (без HITL) — має зростати.
- Entity resolution precision/recall (на розмічених парах).
- Частка `disputed` фактів.

**RAG (найважливіше):**
- **Answer accuracy** на golden set (точність значення + одиниці).
- Citation validity: чи справді джерело містить твердження.
- Route distribution: частка відповідей через exact lookup (A) vs retrieval (B) — зростання A зазвичай = зростання точності.
- Refusal correctness: чесне "невідомо" там, де даних нема (не галюцинація).

## 2. Golden set і регресійні еви

- **Golden set:** курований набір `запит → еталонна відповідь` з різних категорій, рушіїв, форматів (структура, таблиця, PDF, проза, конфлікт).
- **Регресійний прогін на кожен реліз** будь-якого шару пайплайну (новий парсер, нова версія онтології, нова embedding-модель, зміна промпту): порівняти метрики до/після, блокувати реліз при регресії.
- **Категорійні зрізи:** окремо міряти точність по категоріях товарів і типах джерел — деградація часто локальна.
- Окремо — набір "складних" кейсів: багатотоварні сторінки, суперечливі джерела, рідкісні одиниці.

## 3. Моніторинг drift (деградація джерел)

Сайти змінюють структуру → парсери мовчки перестають працювати. Треба ловити автоматично:

- **Coverage drop alert:** різке падіння кількості витягнутих атрибутів по домену/шаблону → сайт змінив розмітку.
- **Schema drift:** зникнення очікуваних селекторів/полів → адаптер застарів.
- **Confidence drift:** зростання частки low-confidence або `disputed` фактів по джерелу.
- **Auto-fallback:** при падінні детермінованих tier-ів по домену — тимчасова ескалація на Tier 4 (LLM), щоб не втратити покриття, + тікет на оновлення адаптера.
- **Anomaly checks на значеннях:** факти поза `value_constraints` (вага навушників 2 т) → карантин + перевірка.

## 4. Human-in-the-loop (HITL)

Люди працюють **лише з винятками**, не з усім потоком:

- **Черга мапінгів:** нові/неоднозначні атрибути й enum-значення → підтвердження → запис у словник (замикає цикл, наступного разу автоматично).
- **Черга low-confidence фактів** і `disputed` конфліктів рівноавторитетних джерел.
- **Черга entity-resolution** для неоднозначних злиттів товарів.
- Пріоритезація черги за впливом (популярні товари/категорії — вперед).
- Кожне рішення людини — навчальний сигнал: поповнює словники/правила, зменшує майбутню ручну роботу.

## 5. Стратегія пере-краулінгу (freshness)

Різні поля змінюються з різною швидкістю — краулити з різною частотою, щоб не палити ресурс і не відставати:

| Тип даних | Частота | Обґрунтування |
|---|---|---|
| Ціна, наявність | Часто (години/день) | Швидко змінюються |
| Характеристики | Рідко (тижні) | Стабільні; змінюються при новій ревізії товару |
| Новий товар | Одразу при discovery | Максимальне покриття |
| Ревалідація "давно не бачених" | За розкладом | Виявити зняті з продажу |

- **Content-hash + conditional requests** (`ETag`/`If-Modified-Since`): не переобробляти незмінене.
- **Адаптивна частота:** товари/домени, що часто змінюються, — частіше; стабільні — рідше.
- **Detекція зникнення:** сторінка 404/redirect → позначити товар як знятий, не видаляти факти (історія).

## 6. Спостережуваність (observability)

- **End-to-end трасування:** від fetch → extraction → normalization → answer, з кореляційним ID.
- **Логи рішень RAG:** маршрут (A/B), використані факти/чанки, згенерована відповідь — для розбору помилок.
- **Дашборди:** coverage, freshness, auto-map rate, answer accuracy, route distribution, блокування per домен.
- **Алерти:** drift, зростання блокувань, падіння grounding rate, ріст черги HITL.

## 7. Зворотний зв'язок від користувачів

- Кнопка "невірна відповідь" → тікет з повним трасуванням → у golden set як новий кейс.
- Патерни скарг → пріоритети для покращення адаптерів/онтології.

## 8. Управління змінами онтології

- Зміна онтології версіонована; ренормалізація — цільова (лише зачеплені атрибути).
- Регресійний прогін після кожної зміни онтології (розділ 2).
- Міграційні нотатки: що змінилось, які факти перераховано.

## 9. Результат шару

Система з вимірюваною якістю, автоматичним виявленням деградації, керованою свіжістю й обмеженим (виключним) людським втручанням. Далі — `07-tech-stack-infrastructure.md`: конкретний стек і інфраструктура.
