# 00. Огляд архітектури: Сервіс здобування характеристик товарів для RAG

## 1. Мета системи

Побудувати сервіс, який:

1. Збирає дані про товари з сайтів виробників (різні CMS, різна структура, антибот-захист).
2. Витягує характеристики зі структурованих блоків **і** з rich-контенту (описи, PDF, зображення).
3. Нормалізує різнорідні таксономії до єдиної канонічної онтології.
4. Зберігає факти з провенансом (джерело, дата, впевненість).
5. Відповідає на запити користувача про характеристики з **максимальною точністю** через гібридний RAG.

## 2. Ключовий архітектурний принцип

> **Характеристика товару — це структурований факт, а не текст.**

Класичний "naive RAG" (нарізати сторінки на чанки → вектори → top-k → LLM) для характеристик працює погано:

| Проблема naive RAG | Наслідок |
|---|---|
| Рядок таблиці "Вага: 2.3 кг" без контексту товару | Retrieval знаходить вагу іншого товару |
| Синоніми атрибутів ("вага" / "маса" / "weight, net") | Embedding не гарантує збіг |
| Одиниці виміру ("230 г" vs "0.23 кг") | LLM плутається при порівнянні |
| Конфлікт версій сторінки | Відповідь застарілими даними |

Тому архітектура — **гібридна, fact-first**:

1. **Canonical Fact Store** — структуроване сховище нормалізованих фактів `(товар, атрибут, значення, одиниця, джерело, confidence)`. Точний lookup — перший маршрут відповіді.
2. **Векторний + лексичний індекс** — fallback для запитів, які не мапляться на канонічний атрибут, та для rich-контенту.
3. **LLM-оркестрація** — розуміння запиту, маршрутизація, генерація відповіді з цитатами.

```
  Seeds    ───▶ │                 politeness)      anti-bot adapters)        │

                │  Tier 3: DOM-евристики (spec-таблиці, dl, key:value)       │
                │  Tier 4: LLM-екстракція (rich text, PDF, OCR/vision)       │

                                            ▼
                ┌────────────────────────────────────────────────────────────┐

                │  Attribute mapping ─▶ Value/unit normalization ─▶          │

                                            │ canonical facts
                                            ▼

                │                         STORAGE                            │
                │  Canonical Fact Store (Postgres/JSONB, версіонований)      │

                                            ▼
                ┌────────────────────────────────────────────────────────────┐
                │                      ANSWERING (RAG)                       │

                │    1) exact fact lookup (SQL / function calling)           │
                │    2) hybrid retrieval (dense + BM25 + filters) ─▶ rerank  │

                └────────────────────────────────────────────────────────────┘
```

## 5. Наскрізні вимоги (cross-cutting)

- **Провенанс усюди.** Кожен факт несе: URL, дату fetch-у, метод екстракції, сирий фрагмент (span), confidence. Без цього неможливі ні citations, ні дебаг, ні вирішення конфліктів.
- **Ідемпотентність пайплайну.** Повторний запуск на тих самих raw-даних дає той самий результат; кожен етап читає з попереднього сховища, а не з "живого" сайту.
- **Версіонування, не перезапис.** Факти не оновлюються in-place — додається нова версія з `valid_from`. Це дає відповіді "станом на дату" і аудит.
- **Каскад за вартістю.** Дешеві детерміновані методи завжди перед дорогими (LLM, headless-браузер). LLM — тільки там, де детермінований парсинг не спрацював.
- **Human-in-the-loop за винятками.** Люди затверджують нові мапінги атрибутів і low-confidence факти, а не переглядають усе.

## 6. Потік даних на прикладі

1. Discovery знаходить `https://vendor.com/products/model-x` через sitemap.
2. Fetcher (детектовано Next.js → достатньо HTTP + парсинг `__NEXT_DATA__`) зберігає raw JSON.
3. Extraction Tier 1 бере `schema.org/Product` з JSON-LD: `{"weight": "2.3 kg", "ip_rating": "IP67"}`. Tier 4 (LLM) додатково з опису: "працює до 14 годин від батареї" → `battery_life: 14 h, confidence 0.86, span="працює до 14 годин"`.
4. Normalization: "weight" → канонічний `net_weight_g = 2300`; товар зматчено за MPN до існуючого product_id.
5. Storage: факти записані з версією; чанки перегенеровані й переіндексовані.
6. Запит "скільки важить Model X?" → router → exact lookup → відповідь "2.3 кг" з посиланням на сторінку виробника й датою.
