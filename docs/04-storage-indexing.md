# 04. Storage & Indexing: сховище фактів і побудова індексів

Мета шару — зберегти канонічні факти так, щоб (а) точний lookup був детермінованим і швидким, (б) векторний/лексичний пошук був якісним завдяки правильному чанкінгу, (в) усе було версіонованим і придатним для аудиту.

## 1. Три сховища, різні задачі

| Сховище | Що тримає | Роль у відповіді |
|---|---|---|
| **Canonical Fact Store** (Postgres/JSONB) | Нормалізовані факти, товари, провенанс, версії | Точний lookup — головний маршрут |
| **Vector + Lexical Index** (pgvector/Qdrant + OpenSearch) | Чанки для семантичного/ключового пошуку | Fallback, rich-контент, нечіткі запити |
| **Knowledge Graph** (опційно) | product—attribute—value, зв'язки, серії | Порівняння, "схожі товари", навігація |

## 2. Canonical Fact Store — схема

Реляційна основа з JSONB там, де потрібна гнучкість.

**`products`** — сутність товару:
`product_id`, `brand`, `model`, `category_path`, `gtin`, `mpn`, `canonical_title`, `source_urls[]`, `created_at`, `updated_at`.

**`facts`** — версіоновані факти (серце системи):
`fact_id`, `product_id`, `attribute_key`, `ontology_version`,
`canonical_value`, `canonical_unit`, `original_value`, `data_type`,
`effective` (bool), `disputed` (bool), `confidence`,
`provenance` (JSONB: source_type, url, tier, span, fetched_at),
`valid_from`, `superseded_by` (fact_id | null).

**`attributes_ontology`** — канонічна онтологія (див. `03`): `attribute_key`, `category_path`, `data_type`, `canonical_unit`, `synonyms[]`, `version`.

**`mapping_dictionary`** — підтверджені мапінги `raw_attribute → attribute_key` (замикання HITL).

**`sources`** — реєстр джерел і статус дозволу (feed/API/scrape/заборонено).

**Індекси БД:** по `(product_id, attribute_key, effective)` для миттєвого lookup; по `gtin`, `mpn`, `brand+model` для entity resolution; GIN по JSONB-provenance за потреби.

## 3. Версіонування фактів (append-only)

- Оновлення = вставка нового рядка `facts` + проставлення `superseded_by` старому.
- **Поточний стан** = `WHERE effective = true AND superseded_by IS NULL`.
- **Стан на дату** = фільтр за `valid_from`.
- Переваги: аудит, "як було", безпечний відкат при регресії парсера, порівняння версій парсера.

## 4. Стратегія чанкінгу (критично для якості RAG)

Головна причина поганого retrieval характеристик — **неконтекстні чанки**. Рядок "Вага: 2.3 кг" без товару знайде вагу будь-чого. Правило: **кожен чанк самодостатній**.

### 4.1 Fact-level чанки (з canonical store)
Кожен факт (або невелика група фактів товару) серіалізується в самодостатній фрагмент з "шапкою" товару:

```
[Бренд: Acme] [Модель: Model X] [Категорія: Навушники]
Вага нетто: 2.3 кг (2300 г).
Клас захисту: IP67.
Час автономної роботи: 14 год.
Джерело: vendor.com, станом на 2026-07-10.
```

- Таблиці специфікацій серіалізуються **атрибут-за-атрибутом у прозу**, не як голі рядки.
- У кожен чанк — ідентифікатори товару (бренд, модель, категорія) → семантичний пошук не сплутає товари.
- Метадані чанку (для фільтрації): `product_id`, `brand`, `category_path`, `attribute_keys[]`, `source_url`, `fetched_at`.

### 4.2 Rich-контент чанки (з опису/PDF)
- Семантичне розбиття прози (за секціями/абзацами), з тією ж "шапкою" товару на початку кожного чанку.
- Зберігати зв'язок чанку з фактами, які з нього витягнуто (для citations).

### 4.3 Синхронність з фактами
- При зміні факту → відповідні чанки перегенеровуються й переіндексовуються (не лишати застарілі вектори).
- Прив'язка `chunk → fact_ids → source_span` для наскрізних цитат.

## 5. Гібридний індекс

Три сигнали, що доповнюють одне одного:

1. **Dense (embeddings):** семантична близькість — ловить синоніми й переформулювання.
2. **Lexical (BM25):** точні збіги термінів, кодів моделей, партномерів — там, де вектори "розмивають".
3. **Metadata-фільтри:** `brand`, `category_path`, `attribute_key`, `effective=true` — звужують простір **до** ранжування, різко піднімаючи точність.

**Порядок:** спершу metadata-фільтр (напр. лише потрібний бренд/категорія) → потім dense+BM25 у відфільтрованому підмножині → далі reranking (див. `05`).

**Вибір векторної БД:**
- **pgvector** — коли хочемо одну БД з фактами (простіше, менше рухомих частин, транзакційна консистентність факт↔вектор).
- **Qdrant/спеціалізована** — коли потрібні масштаб, розширені payload-фільтри, окреме масштабування пошуку.
- **OpenSearch/Elasticsearch** — BM25 + фільтри; може закрити й лексику, і метадані.

## 6. Knowledge Graph (опційно, для порівнянь)

- Вузли: `Product`, `Attribute`, `Value`, `Brand`, `Series`.
- Ребра: `has_attribute`, `belongs_to_category`, `variant_of`, `succeeds`.
- Дає ефективні запити на кшталт "порівняй X і Y за вагою й автономністю", "інші моделі серії з IP67".
- Не замінює fact store — надбудова для реляційно-порівняльних запитів.

## 7. Життєвий цикл індексу

- **Інкрементальне оновлення:** змінені факти → перегенерація лише їх чанків.
- **Реіндексація при зміні embedding-моделі:** повний перерахунок векторів (планова, версіонована подія).
- **Консистентність:** індекс — похідне від fact store; при розбіжності fact store — джерело істини, індекс перебудовується.

## 8. Результат шару

Готові до запитів сховища: точний fact store для детермінованих відповідей і гібридний індекс самодостатніх чанків для семантичних/нечітких запитів. Далі — `05-rag-pipeline.md`: як усе це використати для максимально точної відповіді.
