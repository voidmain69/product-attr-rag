# 09. Testing Requirements: вимоги до тестування

Обов'язкові для кожного PR. CI (`.github/workflows/ci.yml`) блокує мерж при невиконанні.

## 1. Піраміда тестів

| Рівень | Маркер pytest | Що перевіряє | Коли запускається |
|---|---|---|---|
| Unit | (без маркера) | чиста логіка: парсери, нормалізація, конверсія одиниць, моделі | кожен коміт, CI |
| Integration | `@pytest.mark.integration` | взаємодія з Postgres/RabbitMQ/MinIO з docker-compose | CI на PR, локально `dev.py test-all` |
| Golden / eval | `@pytest.mark.golden` | регресія якості extraction/normalization/RAG на golden set | кожен реліз, зміни парсерів/промптів/онтології |

Мінімум: **coverage ≥ 80%** по `src/attrpipe` (поріг у `pyproject.toml`, `fail_under`). Coverage — нижня межа, не ціль: тести пишуться на поведінку, не на рядки.

## 2. Жорсткі правила

1. **Жодних звернень до живих сайтів у тестах.** Усі HTML/JSON/PDF-входи — фікстури в `tests/fixtures/` (реальні збережені сторінки, анонімізовані за потреби). Мережа в unit-тестах мокається; випадковий мережевий виклик = падіння тесту.
2. **Жодних реальних LLM-викликів в unit/integration.** LLM-відповіді — записані фікстури (recorded responses). Реальні виклики — тільки в golden-евалах, явно й з бюджетом.
3. **Детермінізм.** Тест, що флейкає, — це баг: фіксувати seed, час — через injectable clock, без sleep-ів.
4. **Тести пишуться разом з кодом**, в одному PR. Багфікс починається з тесту, який відтворює баг.
5. **Кожен новий екстрактор/адаптер** приходить з фікстурою реальної сторінки відповідного рушія і перевіркою: очікувані `raw_attribute/raw_value/span`.
6. **Нормалізація:** для кожного нового `data_type`/одиниці — табличні тести (parametrize) на крайові випадки: локалі ("2,3 кг"), діапазони, аномалії поза `value_constraints`.
7. **Провенанс перевіряється явно:** тест екстракції завжди assert-ить, що `source_span` реально міститься у вхідному артефакті (анти-галюцинаційний інваріант з `02 §5.3`).

## 3. Golden set (регресія якості)

- `tests/golden/` — курований набір `запит → еталонна відповідь` + сирі артефакти; покриває категорії, рушії, формати (структура/таблиця/PDF/проза/конфлікт/відсутні дані).
- Прогін обов'язковий перед мержем змін у: парсери (будь-який tier), промпти, онтологію, embedding-модель, логіку маршрутизації RAG.
- Метрики прогону: answer accuracy (значення+одиниця), citation validity, route distribution, refusal correctness (чесне "невідомо").
- **Регресія будь-якої метрики нижче зафіксованого базового рівня = блокер мержа.** Базовий рівень оновлюється свідомим комітом разом з поясненням.
- Кожна репортована користувачем помилка додається у golden set як кейс перед фіксом.

## 4. Integration-тести

- Піднімаються проти локального docker-compose (`python tools/dev.py up`); у CI — service containers.
- Кожен тест створює й прибирає свої дані (унікальні ключі, teardown); не залежить від порядку виконання.
- Обов'язкові сценарії: append-only версіонування фактів (supersede, "стан на дату"), exact lookup route, ідемпотентність повторної обробки того самого `raw_artifact_id`.

## 5. Що НЕ тестуємо

- Сторонні бібліотеки та їхні контракти (довіряємо версіям, зафіксованим у lock/CI).
- Приватні функції напряму — тільки через публічну поведінку модуля.
- Точні тексти LLM-відповідей — тільки структуру, grounding і citations.

## 6. Запуск

```bash
python tools/dev.py test        # unit
python tools/dev.py test-all    # + integration (потрібен docker compose up)
python tools/dev.py cov         # unit + coverage звіт
pytest -m golden                # golden-еваль (потрібен ANTHROPIC_API_KEY)
```
