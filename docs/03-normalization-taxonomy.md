# 03. Normalization & Taxonomy: приведення до єдиної онтології

Це найскладніший і найважливіший для точності шар. Умова прямо ставить проблему: **таксономії у всіх виробників різні**. Один атрибут у різних джерел зветься по-різному ("Вага" / "Маса" / "Weight, net" / "Вес нетто"), має різні одиниці ("2.3 кг" / "2300 г" / "2300g"), різні формати (enum, boolean, діапазон). Мета шару — звести цей хаос до єдиного канонічного представлення, придатного для точного lookup і надійного порівняння.

## 1. Канонічна онтологія атрибутів

Власна, версіонована модель атрибутів, організована по категоріях товарів.

**Структура канонічного атрибута:**

```json
{
  "attribute_key": "net_weight",
  "category_path": ["electronics", "audio", "headphones"],
  "display_name": {"uk": "Вага нетто", "en": "Net weight"},
  "data_type": "quantity",            // quantity | enum | boolean | text | range | date
  "canonical_unit": "g",              // базова одиниця для quantity
  "allowed_units": ["g", "kg", "oz", "lb"],
  "value_constraints": {"min": 0, "max": 500000},
  "enum_values": null,                // для data_type=enum
  "synonyms": ["вага", "маса", "weight", "вес нетто", "mass"],
  "version": 4
}
```

**Категорійність обов'язкова:** "роздільна здатність" у камери й у монітора — різні атрибути з різними одиницями й діапазонами. Онтологія — це дерево категорій, де кожна категорія додає/успадковує набір атрибутів.

**Версіонування онтології:** зміна схеми (новий атрибут, зміна одиниці) → нова версія. Факти зберігають, за якою версією онтології їх нормалізовано, щоб уникнути мовчазних розбіжностей.

## 2. Мапінг чужих таксономій → канон (attribute mapping)

Головний рушій точності. Багатоступеневий, від дешевого до дорогого:

### 2.1 Ступінь 1 — словник (детермінований, миттєвий)
- Таблиця відомих синонімів `raw_attribute → attribute_key` (у т.ч. з урахуванням мови й категорії).
- Найшвидший і найточніший шлях; покриває більшість повторюваних кейсів.
- Постійно поповнюється підтвердженими мапінгами (замикання HITL-циклу).

### 2.2 Ступінь 2 — embedding-similarity (кандидати)
- Embedding назви `raw_attribute` (+ контекст: категорія, приклад значення) → пошук найближчих канонічних атрибутів.
- Дає ранжований список кандидатів з оцінкою схожості.
- Поріг: висока схожість + унікальний лідер → автоматичний мапінг; інакше → на суддю.

### 2.3 Ступінь 3 — LLM-суддя (неоднозначні/нові)
- LLM отримує: `raw_attribute`, приклад значення, категорію, топ-N канонічних кандидатів.
- Завдання: обрати кандидата **або** запропонувати "новий атрибут".
- Вихід структурований: `{decision: map|new|reject, attribute_key?, confidence, rationale}`.

### 2.4 Ступінь 4 — Human-in-the-loop (затвердження)
- **Нові атрибути** та low-confidence мапінги потрапляють у чергу модерації.
- Людина підтверджує/коригує → рішення записується у словник (ступінь 1) → наступного разу спрацьовує автоматично.
- Так система **навчається**: ручна робота одноразова на кожен новий патерн, а не постійна.

> Ключова ідея: люди не переглядають усе — лише **невідоме раніше**. З часом частка автоматичних мапінгів зростає.

## 3. Нормалізація значень (value normalization)

Після того як атрибут зіставлено, нормалізуємо саме значення відповідно до `data_type`:

### 3.1 Quantity (число + одиниця)
- Парсинг числа й одиниці з "сирого" значення ("2,3 кг", "2.3kg", "2300 g").
- Конверсія в `canonical_unit` ("2.3 кг" → `2300 g`).
- Зберігаємо і канонічне (`2300 g`), і оригінальне представлення (для показу як у джерела).
- Валідація по `value_constraints` (вага 2300000 г для навушників → аномалія → на перевірку).

### 3.2 Range (діапазон)
- "від -10 до +40 °C", "10–20 000 Гц" → `{min, max, unit}` у канонічних одиницях.

### 3.3 Enum
- Мапінг варіантів написання на канонічні значення ("USB Type-C" / "USB-C" / "Type C" → `usb_c`).
- Той самий підхід (словник → embedding → LLM), що й для атрибутів.

### 3.4 Boolean
- "Так/Ні", "Yes/є/присутній", "✓", "N/A" → `true/false/unknown`.

### 3.5 Text (вільні характеристики)
- Мінімальна нормалізація (тримінг, мова), зберігання як є; такі поля переважно йдуть у векторний індекс, а не в точний lookup.

### 3.6 Одиниці локалі
- Десяткова кома vs крапка, роздільники тисяч, локальні одиниці — обробляти явно за мовою джерела.

## 4. Entity Resolution (матчинг товарів)

Той самий товар зустрічається на кількох сторінках/джерелах під різними URL і назвами. Треба звести їх до одного `product_id`, інакше факти "розмажуться".

**Ключі матчингу (за спаданням надійності):**
1. **GTIN/EAN/UPC** — глобальний ідентифікатор, найнадійніший.
2. **MPN + Brand** — партномер виробника в межах бренду.
3. **Brand + нормалізована модель** — коли немає GTIN/MPN.
4. **Fuzzy** (назва + ключові атрибути + зображення-embedding) — крайній випадок, з нижчою впевненістю.

**Процес:**
- Blocking (згрупувати кандидатів за брендом/категорією, щоб не порівнювати всіх з усіма).
- Порівняння в межах блоку за ключами вище.
- Поріг злиття; неоднозначні пари → HITL.
- Зберігати **всі URL-джерела** під одним `product_id` (граф "product ← sources").

## 5. Вирішення конфліктів (conflict resolution)

Різні джерела дають різні значення того самого канонічного атрибута. Не мовчазний перезапис, а явне рішення з правилами:

**Правила пріоритету (комбінуються у зважену оцінку):**
1. **Тип джерела:** офіційний фід/API виробника > structured data (Tier 1) > CMS-адаптер (Tier 2) > DOM-евристика (Tier 3) > LLM з прози (Tier 4).
2. **Свіжість:** новіший `fetched_at` вагоміший (особливо для мінливих полів).
3. **Консенсус:** якщо кілька незалежних джерел збігаються — впевненість росте.
4. **Confidence екстракції:** вища — вагоміша.
5. **Валідність:** значення поза `value_constraints` — штраф/відкидання.

**Вихід:**
- Обирається "діюче" (`effective`) значення + зберігаються **всі** конкуруючі варіанти з їх провенансом.
- При суттєвому конфлікті рівноавторитетних джерел — прапор `disputed` (у відповіді RAG це показується явно, а не приховується — див. `05-rag-pipeline.md`).

## 6. Модель канонічного факту (вихід шару)

```json
{
  "product_id": "prd_01H...",
  "attribute_key": "net_weight",
  "ontology_version": 4,
  "canonical_value": 2300,
  "canonical_unit": "g",
  "original_value": "2.3 кг",
  "data_type": "quantity",
  "effective": true,
  "disputed": false,
  "confidence": 0.94,
  "provenance": {
    "source_type": "json_ld",
    "source_url": "https://vendor.com/products/model-x",
    "extraction_tier": 1,
    "source_span": "\"weight\": \"2.3 kg\"",
    "fetched_at": "2026-07-10T12:00:00Z"
  },
  "valid_from": "2026-07-10T12:05:00Z",
  "superseded_by": null
}
```

## 7. Версіонування фактів (не перезапис)

- Нове значення не затирає старе — старий факт отримує `superseded_by`, новий — `valid_from`.
- Дає відповіді "станом на дату", повний аудит і безпечний відкат при помилці парсера.
- Деталі зберігання — у `04-storage-indexing.md`.

## 8. Дельта-обробка

- Якщо `content_hash` артефакту не змінився з минулого разу — переекстракцію/ренормалізацію можна пропустити (крім випадку, коли змінилась версія онтології чи методу).
- Зміна онтології → цільова ренормалізація лише зачеплених атрибутів, не всієї бази.

## 9. Результат шару

Набір канонічних, нормалізованих, дедуплікованих фактів з провенансом і статусом конфлікту, прив'язаних до стабільного `product_id`. Це і є "джерело істини" для точних відповідей. Далі — `04-storage-indexing.md`: як це зберігати та індексувати для гібридного пошуку.
