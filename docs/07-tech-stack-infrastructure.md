# 07. Tech Stack & Infrastructure: стек, черги, масштабування

Мета — конкретизувати технологічні вибори й інфраструктурні патерни. Наведені варіанти орієнтовні; ключові — не назви продуктів, а архітектурні властивості (черги, ідемпотентність, розділення дешевих/дорогих шляхів, версіонування).

## 1. Компоненти по шарах

| Шар | Задача | Орієнтовний вибір |
|---|---|---|
| Discovery | sitemap/feed/каталог парсинг | власні парсери + планувальник |
| Static fetch | HTTP з fingerprint-impersonation | httpx / curl_impersonate |
| Headless fetch | рендер SPA, перехоплення XHR | Playwright / Camoufox (стелс) |
| Проксі | residential/mobile ротація | комерційний проксі-провайдер |
| Черги | розв'язка шарів, backpressure | Kafka / RabbitMQ / SQS |
| Raw store | сирі артефакти | S3-сумісне об'єктне сховище |
| HTML→Markdown | очищення rich-контенту | trafilatura / readability |
| PDF | текст/таблиці/OCR | pdfplumber + OCR (Tesseract) |
| Vision/OCR | інфографіка-специфікації | vision-LLM |
| LLM-екстракція | structured output зі схемою | LLM з JSON-schema / function calling |
| Embeddings | вектори чанків/атрибутів | багатомовна embedding-модель |
| Fact store | канонічні факти | PostgreSQL + JSONB |
| Vector index | семантичний пошук | pgvector (просто) або Qdrant (масштаб) |
| Lexical index | BM25 + фільтри | OpenSearch / Elasticsearch |
| Reranker | cross-encoder переранжування | bge-reranker / cohere-rerank |
| Orchestration | пайплайни, розклад | Airflow / Temporal / Dagster |
| HITL UI | черги модерації | внутрішній веб-застосунок |

## 2. Стиль архітектури: черги між шарами

Кожен шар читає з черги/сховища попереднього й пише в наступне. Переваги:

- **Розв'язка темпів:** повільний headless-fetch не блокує швидку екстракцію готових даних.
- **Backpressure:** downstream перевантажений → сповільнюємо upstream, не втрачаємо дані.
- **Ретраї й dead-letter:** збійні одиниці ізолюються, не валять пайплайн.
- **Ідемпотентність:** повторна обробка того самого повідомлення дає той самий результат (ключ = `raw_artifact_id` + версія методу).
- **Незалежне масштабування:** масштабуємо саме вузьке місце (частіше — headless-fetch і LLM-екстракцію).

```
discovery.q ─▶ [Discovery] ─▶ fetch.q ─▶ [Fetcher pool] ─▶ raw.store
raw.events  ─▶ [Extraction] ─▶ facts.candidates.q ─▶ [Normalization] ─▶ fact.store
fact.events ─▶ [Indexer] ─▶ vector+lexical index
                                    ▲
                          [RAG service] ──── query API
```

## 3. Розділення дешевого й дорогого шляхів

Найдорожчі ресурси — **headless-браузер** і **LLM-виклики**. Архітектура мінімізує їх:

- Static-first fetch; headless лише при потребі.
- Tier 1–3 екстракція перед Tier 4; LLM тільки на непокрите.
- Кеш LLM-екстракції по `(content_hash, schema_version, method_version)` — не платити двічі за той самий контент.
- Пакетування (batching) LLM-запитів де можливо.

Це прямо впливає на юніт-економіку: більшість товарів мають закриватись дешевими детермінованими шляхами; LLM — "довгий хвіст" складних rich-кейсів.

## 4. Масштабування

- **Fetcher pool:** горизонтально, з пулом воркерів на static і окремим — на headless (різні профілі ресурсів).
- **Per-domain шардинг:** політики politeness прив'язані до домену; розподіл по воркерах з урахуванням доменних лімітів.
- **Extraction/Normalization:** stateless-воркери, масштабуються за глибиною черги.
- **Fact store:** партиціонування по категорії/бренду; read-репліки під RAG-навантаження.
- **Vector index:** шардинг/реплікація (Qdrant) при великій кількості чанків.
- **RAG service:** stateless, за load balancer; кеш частих запитів.

## 5. Надійність і консистентність

- **Fact store — джерело істини;** індекси — похідні, перебудовувані.
- **Транзакційність факт↔вектор** простіша з pgvector (одна БД); при роздільних сховищах — outbox-патерн для узгодження.
- **Бекапи** fact store і raw store; raw store дозволяє повну реекстракцію без нового краулу.
- **Reprocessing pipeline:** прогнати нову версію парсера/онтології по історичних raw-даних без звернень до сайтів.

## 6. Безпека й доступ

- Ізоляція fetch-воркерів (виконують ненадійний контент сайтів) від внутрішньої мережі.
- Секрети (проксі, LLM-ключі) у секрет-менеджері.
- Обмежений, параметризований доступ RAG-шару до fact store (function calling, не сирий SQL від LLM).
- Реєстр джерел з правовим статусом (див. `01`) як частина compliance.

## 7. Орієнтовна вартість (де витрати)

| Стаття | Драйвер | Оптимізація |
|---|---|---|
| Проксі-трафік | обсяг fetch, headless | static-first, кеш, conditional requests |
| Headless-час | частка SPA | перехоплення XHR замість рендер-скрейпу |
| LLM-токени | Tier 4 екстракція, RAG-генерація | каскад, кеш, схеми, batching |
| Embeddings | к-сть/розмір чанків | інкрементальна реіндексація |
| Зберігання | raw + версії фактів | ретенція, стиснення |

## 8. Дорожня карта впровадження (порядок)

1. **MVP точності:** discovery → static fetch → Tier 1 (structured data) → мінімальна онтологія (1–2 категорії) → fact store → exact lookup RAG. Уже дає точні відповіді на структурованих сайтах.
2. **Розширення екстракції:** CMS-адаптери (Tier 2), DOM-евристики (Tier 3), headless для SPA.
3. **Rich-контент:** Tier 4 LLM + PDF/vision; grounding-верифікація.
4. **Нормалізація в масштабі:** embedding+LLM мапінг, HITL-черги, entity resolution.
5. **Hybrid retrieval:** чанкінг, вектори+BM25+rerank як fallback.
6. **Операційна зрілість:** golden set, drift-моніторинг, адаптивний пере-краулінг, дашборди.

Порядок навмисне ставить **точність на структурованих даних** першою: вона дає максимальну віддачу за мінімальних зусиль, а дорогі шляхи (headless, LLM) додаються там, де дешеві не покривають.

## 9. Підсумок

Стек підпорядкований трьом принципам усієї архітектури: **fact-first точність**, **каскад за вартістю**, **версіонування й провенанс усюди**. Технології змінні; ці принципи — ні.
