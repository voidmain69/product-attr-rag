# 02. Extraction: здобування характеристик із сирих артефактів

Мета шару — перетворити сирі артефакти (HTML/JSON/PDF/зображення з Raw Store) на **кандидат-факти**: пари `атрибут → значення` у "сирому" вигляді джерела, кожна з провенансом, span-цитатою та впевненістю. Нормалізація й приведення до канону — наступний шар.

## 1. Принцип каскаду за вартістю

Екстракція йде **зверху вниз**, від найдешевшого й найточнішого до найдорожчого. Наступний tier застосовується лише коли попередній не покрив потрібне.

```
Tier 1  Structured data (JSON-LD / microdata / OG)     ── найдешевше, найточніше
Tier 2  CMS/engine-адаптери (відомі селектори/API)
Tier 3  DOM-евристики (spec-таблиці, dl, key:value)
Tier 4  LLM-екстракція (rich text, PDF, vision)        ── найдорожче, найгнучкіше
```

Кожен tier додає факти в спільний пул кандидатів. Якщо Tier 1 дав "вагу", Tier 4 не витрачає токени на неї — але може додати атрибути, яких не було в структурі (напр. згадані лише в описі).

## 2. Tier 1 — Structured data

Найкраще джерело: виробник сам розмітив дані для пошуковиків.

- **JSON-LD** `schema.org/Product` (+ `Offer`, `PropertyValue`, `additionalProperty`) — часто містить назву, бренд, GTIN/MPN, ціну, іноді специфікації.
- **Microdata / RDFa** — старіший формат тієї ж семантики.
- **Open Graph / Twitter Cards** — назва, зображення, іноді ціна.
- **Вбудований JSON фреймворків:** `__NEXT_DATA__`, `window.__NUXT__`, Apollo/GraphQL-стейт, `/products/x.json` (Shopify). Це часто **найбагатше** джерело — повна модель товару, включно з атрибутами, яких немає у видимому HTML.

Витяг детермінований, span = шлях у JSON. Confidence висока (≈0.95+).

## 3. Tier 2 — CMS/engine-адаптери

Для розпізнаного рушія (з `01-crawling.md`) застосовуємо готовий адаптер:

- Відомі CSS/XPath-селектори spec-блоків конкретної CMS/теми.
- Відомі API-ендпоінти (Shopify `.json`, Woo REST, Magento GraphQL).
- Мапінг типових полів рушія на попередню (ще не канонічну) схему.

Адаптери — це **бібліотека шаблонів**, що росте. Кожен новий часто-вживаний рушій/тема → новий адаптер, який знімає навантаження з дорогого Tier 4.

## 4. Tier 3 — DOM-евристики

Коли структури немає й адаптера немає — евристичний парсинг очищеного DOM:

- **Spec-таблиці:** `<table>` з двома колонками → key/value; `<th>`/`<td>` пари.
- **Списки визначень:** `<dl>`/`<dt>`/`<dd>`.
- **Патерни "Ключ: значення"** у рядках (`Вага: 2.3 кг`).
- **Секції "Характеристики"/"Specifications"** за заголовками.
- Евристики розпізнавання одиниць і чисел для валідації, що це справді характеристика, а не маркетинговий текст.

Confidence середня; кожен факт несе span (селектор/текст), щоб downstream міг перевірити.

## 5. Tier 4 — LLM-екстракція (rich-контент, PDF, зображення)

Тут закривається головна проблема з умови: **частина характеристик живе в rich-контенті** — у прозі опису, у PDF-datasheet, на зображенні-інфографіці.

### 5.1 Підготовка входу
- HTML → чистий Markdown (видалити навігацію, футер, скрипти; лишити основний контент). Це різко зменшує токени й шум.
- PDF → текст (текстовий шар) або, для сканів, → зображення сторінок для OCR/vision.
- Зображення зі специфікаціями → vision-модель.

### 5.2 Structured output зі схемою категорії
LLM викликається **з JSON-схемою очікуваних атрибутів для категорії товару** (не "витягни все підряд", а "заповни цю схему, чого немає — null"). Це:
- зменшує галюцинації (закритий перелік полів),
- дає одразу типізований вихід,
- дозволяє валідацію.

**Обов'язкові поля кожного витягнутого факту:**
- `value` — значення як у джерелі;
- `unit` — одиниця, якщо є;
- `confidence` — 0..1;
- `source_span` — **дослівна цитата з тексту-джерела**, з якої взято факт;
- `evidence_location` — де саме (абзац/сторінка PDF/координати на зображенні).

`source_span` критичний: він дає (а) майбутні citations у відповідях, (б) можливість автоматичної верифікації "чи справді цей текст містить це значення".

### 5.3 Захист від галюцинацій
- **Grounding-перевірка:** значення факту має бути присутнє/виводитись зі `source_span`; якщо ні — факт відкидається або знижується confidence.
- **Заборона добудовувати** відсутнє ("невідомо" замість вигаданого).
- Розбиття довгих документів на секції з окремими викликами (уникнення переповнення контексту й змішування товарів).
- Для сторінок з кількома товарами — спершу сегментація "який блок якому товару належить", потім екстракція в межах блоку.

## 6. Модель кандидат-факту (вихід шару)

Кожен факт — запис приблизно такої форми:

```json
{
  "product_ref": {"url": "...", "detected_ids": {"mpn": "...", "gtin": "..."}},
  "raw_attribute": "Вес нетто",
  "raw_value": "2.3",
  "raw_unit": "кг",
  "extraction_tier": 4,
  "extraction_method": "llm_structured_v3",
  "confidence": 0.88,
  "source_span": "Вес нетто изделия составляет 2.3 кг",
  "evidence_location": {"type": "html", "selector": "div.desc > p:nth-child(4)"},
  "raw_artifact_id": "s3://raw/....html",
  "fetched_at": "2026-07-10T12:00:00Z"
}
```

Зверни увагу: **`raw_attribute` ще НЕ канонічний** ("Вес нетто", не `net_weight`). Мапінг — у `03-normalization-taxonomy.md`.

## 7. Злиття кандидатів у межах товару

Один атрибут може прийти з кількох tier-ів/джерел. На виході Extraction ми **не вирішуємо конфлікт остаточно** (це робить нормалізація з урахуванням пріоритетів джерел), але:
- групуємо кандидати за `(product_ref, raw_attribute)`;
- зберігаємо **всі** варіанти з їх confidence і провенансом;
- позначаємо збіги/розбіжності для наступного шару.

## 8. Провенанс і відтворюваність

- Кожен факт прив'язаний до `raw_artifact_id` — можна переекстрагувати без нового краулу.
- Версія методу екстракції (`extraction_method`) фіксується → при покращенні парсера видно, що змінилось і чому.
- Ідемпотентність: той самий raw + та сама версія методу = той самий вихід.

## 9. Результат шару

Пул кандидат-фактів з "сирими" (ще не нормалізованими) атрибутами, значеннями, одиницями, span-цитатами й confidence. Далі — `03-normalization-taxonomy.md`: приведення до єдиної онтології, нормалізація одиниць, матчинг товарів і вирішення конфліктів.
